- **Batch 5 (17 Oct, uncommitted): student↔tutor queries and a staff view of one student's progress.** Built by four parallel subagents against a written API contract, then integrated and verified by the orchestrator. Migration `20261017154243_course_queries`.
  - **Queries are Q&A threads** a student raises on a course they are enrolled in, optionally pinned to a lesson. `CourseQuery` + `CourseQueryMessage` (the author is a `User`, so student, tutor and a master stepping in sit in one list). **Status is who the thread is waiting on**: `OPEN` (a tutor), `ANSWERED` (the student), `RESOLVED` (closed). Posting flips it automatically, so neither side sets state by hand. **Only the student resolves, and RESOLVED is final** — further messages are 409, and there is no staff resolve route at all. New module `backend/src/modules/queries/` (11 routes across student/tutor/master); frontend `components/queries/` plus `/student|tutor|master/queries` and `/queries/[id]`. Queries is a nav tab for all three roles.
  - **Scope**: a student sees only their own threads; a tutor sees threads on courses they own; a master sees everything. Out-of-scope ids are **404, never 403**, so a tutor cannot probe for another tutor's threads. The staff inbox is a work queue — `orderBy: [{ status: 'asc' }, { lastMessageAt: 'desc' }]`, which is exactly OPEN→ANSWERED→RESOLVED because Postgres sorts the enum in declaration order — and defaults its filter to Open.
  - **Staff can open one student and see their progress**: `GET /tutor/students/:id` (the tutor's own courses) and `GET /master/students/:id` (all), rendered by one shared `student-progress-view.tsx` so both roles see the same screen. Per course: percent, which lessons are ticked, last activity, and how each assessment went. Reached by clicking a row in the existing students list.
  - **Assessment standing now has one implementation**: `backend/src/modules/assessments/assessment-standing.util.ts` (`computeAssessmentStanding`). The student's own assessment list and the staff progress view both read from it, so the two can never disagree about whether someone passed. Verified identical through both endpoints after the extraction.

## Decisions (settled, do not re-open)

| Topic | Decision | Why |
|---|---|---|
| Hosting | One AWS Lightsail instance, Mumbai, 4 GB / 2 vCPU / 80 GB, Ubuntu 24.04, Docker Compose | Fixed INR-billed price, users in India, 4 GB needed for `next build` |
| TLS / proxy | Caddy with automatic Let's Encrypt | Zero cert ops |
| Database | Postgres in a container, nightly `pg_dump` to a Lightsail bucket, daily snapshots | Managed DB doubles cost for no benefit at this scale |
| Files and video | Stored on the instance disk, streamed by NestJS with signed 1 h URLs and HTTP Range | Instance has 2 TB/mo transfer; bucket egress would blow the budget |
| Deploy | SSH in and run `scripts/deploy.sh` | Simplest for one developer; GitHub Actions push-to-deploy is an optional later step |
| Monitoring | UptimeRobot health + backup heartbeat, Lightsail status-check alarm | Free |
| Budget | ≈ ₹3,300/month incl. GST, cap ₹5,000 | User constraint |
| If more storage is ever needed | Lightsail block-storage disk first; Cloudflare R2 (zero egress) if object storage is unavoidable | Keeps video egress off metered buckets |
| Student downloads | Students can NEVER download source material (video, PDF, PPTX, any file). View-only in the app; the student download endpoint goes away and the PDF viewer must hide download/print (pdf.js, not the native Chrome viewer) | Course IP protection (user, 17 Oct 2026). Deterrent, not DRM: screen capture is always possible |
| Progress | Formal completion tracking (per-student lesson completions, progress %, Continue button). Non-sequential by default; lessons are never locked | Confirmed by user 17 Oct 2026 |
| Credentials | Admin-only. Admin creates the user with email + temporary password; user must change it at first login. No self-registration, no email invites | User, 17 Oct 2026 |
| Course ownership | Every course and file is company material and must stay in the DB. A course is owned by one tutor. Removing a tutor never deletes courses or files: they become unassigned, visible only to admin, who reassigns them to another tutor. Admin has full read/write on all students, tutors, courses and materials | User, 17 Oct 2026. Means Course.tutorId becomes nullable with SetNull, user delete must not cascade to courses, and "remove tutor" should be deactivate, not delete |
| Admin privileges | The admin can do everything a tutor can on any course (create, edit, lessons, files, enrol, publish, announcements) and can deactivate a course with a reason; reactivation returns it to draft | User, 17 Oct 2026 ("they can literally do anything in the platform") |
| Queries | Student-raised Q&A threads on a course, optionally a lesson. Status is who the thread is waiting on (OPEN/ANSWERED/RESOLVED) and flips automatically as each side posts. **Only the student resolves, and that is final** — a resolved thread rejects new messages; raise a new query instead. Tutors see their own courses' threads, masters see all, out-of-scope ids are 404 | User, 17 Oct 2026 |
| Student progress | A tutor opens a student from the students list and sees per-course lessons, percent and assessment standing, scoped to the tutor's own courses; master sees every course through the same screen | User, 17 Oct 2026 |
| Assessments | Course-level only. Two kinds: auto-graded MCQ and tutor-graded DOCUMENT upload. Tutor sets the pass % per assessment (default 70). Retries unlimited, best score counts, a pass cannot be retaken **Never gated on course progress** — an assessment can be attempted as soon as it is published, even on an unskippable course with lessons still locked. Students reach them from the course detail page; there is no student assessments tab | User, 17 Oct 2026 |
| Lesson completion | A lesson is complete when the student has reached the end of every file attached to it (last PPTX slide, ~95% of a video, a confirmation for PDFs). Deterrent, not DRM | User, 17 Oct 2026 |
| Study materials | Uploaded files only (no external links), attached to a course, visible to enrolled students in the Materials tab | User, 17 Oct 2026 |
| File storage model | One `CourseFile` table discriminated by `purpose`, not five tables. Keeps a single upload/stream/delete pipeline; the cost is that every listing query must filter on purpose | Orchestrator, 17 Oct 2026 |
| Motion | CSS `linear()` spring curves, no motion library. A library only earns its place for velocity handoff from a real drag gesture, and this app has none | Design agent, 17 Oct 2026 |
| Course material model | Keep it simple: a file is uploaded to a course and optionally attached to one lesson (current model). Tutor and admin can attach/detach. Only browser-viewable types are accepted (PDF, PPTX, MP4) because students cannot download | User, 17 Oct 2026 |
